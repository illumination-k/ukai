要約

先に結論。

3 製品はいずれも 「ターミナル多重化 + タスクごとの git worktree + 差分を見て land する」 という同じ骨格を持つ。ukai はそこを狙っていないので、UI の表層（未読・通知・差分への行コメント・添付）は既に追いついているが、 エージェントの成果物を人が受け取る最後の一区間（作業ツリーの差分を見て、commit して、PR にする）が丸ごと空いている。gateway が Pod の中で作業させる設計なので、ここが無いと「エージェントは動いたが成果を取り出せない」が起きる。最優先はこれ（提案 5・7）。

一方で ukai は 3 製品が誰も持っていない ACP ネイティブ・HTTP/WS 一級・Kubernetes での実行・HTML レポート pane を持っている。ここは真似しに行くのではなく、ACP の未使用機能（セッションモード、slash コマンド、terminal/*）を埋めて差を広げるほうが費用対効果が高い（提案 1・2・9）。コスト 2.0 以下で効く細かいもの（要対応へのジャンプ、プロンプトのキュー、リサイズ）は、競合が全部持っていて ukai に無いので早めに潰したい。

調査方法と限界。 各製品の公開 README・ドキュメントサイトを読んだだけで、ソースコードは読んでいない。機能マトリクスの ? は「公開ドキュメントで確認できなかった」であって「無い」ではない。hermes-ide のリモート実行と MCP、orca の ACP クライアント対応の有無はとくに未確認。

比較対象

何者で、どういう骨格を持っているか。

orca

stablyai/orca · MIT · デスクトップ (Electron 系) + モバイル

「ADE（agent development environment）」。1 タスク = 1 git worktree で、40 以上の CLI エージェントを並列に走らせる。

  • 同じプロンプトを複数エージェントに fan-out して勝者を merge
  • VS Code のエディタ、WebGL ターミナル分割、cross-worktree 検索
  • 差分の行コメントをまとめてエージェントに返す
  • SSH worktree（リモートマシンで実行、自動再接続・port forward）
  • モバイルコンパニオン（完了通知と追い指示）
  • Design Mode: 実 Chromium の要素をクリックして HTML/CSS/スクショをプロンプトに送る
  • CLI (orca worktree create / snapshot / click) でエージェント自身が orca を操作
  • GitHub / Linear の PR・issue・ボードをアプリ内で閲覧

herdr

herdrdev/herdr · Apache-2.0 · Rust 単一バイナリ TUI

「エージェントが住むランタイム」。tmux の置き換えに近く、pane = 実 PTY。常駐のセッションサーバーと薄いクライアントに分かれ、Unix socket / SSH 経由でつなぐ。

  • detach してもエージェントは走り続ける（sleep・WiFi 切断・SSH 切断に耐える）
  • session → workspace → tab → pane の階層。複数マシンを 1 画面に
  • 全 pane に working / blocked / idle / done / unknown の状態。PTY 出力からの自動検出 + pane.report_agent での自己申告
  • socket API: agent.* / pane.* / tab.* / workspace.* / layout.* / worktree.*。events.subscribe で push、pane.wait_for_output で待ち合わせ
  • エージェント同士が pane を立てて互いを待てる
  • プラグインマーケットプレイス

hermes-ide

hermes-hq/hermes-ide · BUSL-1.1 → Apache-2.0 · デスクトップ

「あらゆるコーディングエージェントのための 1 つのコンソール」。タスク = ブランチ hermes/<name> + worktree で、入力待ちの エージェントを 1 つの inbox に集める。

  • ⌘I で「自分を待っているエージェント」へジャンプ（attention inbox）
  • Review Desk (⌘G): 変更をターン単位 / ファイル単位で表示、risk flag 付き、行コメントを書いたエージェントに返す
  • ターン単位の diff と restore（巻き戻し）
  • Land: commit → PR 作成 / ローカル merge を 1 操作で
  • タスクごとにエージェント・モデル・effort・アカウントを選び、組み合わせを preset 保存
  • 通知は「いま見ていないセッション」に限る
  • 右/下への pane 分割、GPU ターミナル

ukai が既に持っている差別化点

真似される側。比較の前にここは守る前提で考える。

ACP ネイティブ

3 製品はどれも PTY を覗いてエージェントの状態を推測している（herdr は自己申告 API も用意しているが、結局エージェント側の協力が必要）。ukai は session/update と stopReason をそのまま畳むので、working / blocked が構造として手に入る。plan・ツール呼び出し・パーミッションも同様。

HTTP / WebSocket が一級

競合は「ローカルで CLI を起動」が前提で、リモートは SSH で手元の体験を遠隔に伸ばす形。ukai は ACP の Streamable HTTP / WebSocket で最初からサーバー側のエージェントにつなぐので、クライアントが 落ちてもセッションはサーバーに残る。

Kubernetes 実行（gateway + relay）

ワークスペースごとに Pod を立て、接続より長生きするセッション・ターンの継続・保留中パーミッションの再提示まで持つ。SSH の 1 台より横に伸び、CRD も cluster-scoped な権限も要らない。競合に相当物はない。

HTML レポート pane

エージェントが書いた HTML / 画像を、IPC を持たない子 WebView + 配信範囲の制限 + CSP で安全に pane に出す。競合はプレビュー（Markdown / 画像 / PDF）止まりで、「エージェントの成果物が HTML である」ことを一級に扱っていない。このレポート自体がその用途。

# 提案 分類 効果 コスト 優先 出どころ

提案の詳細

P0 — まずやる

05

作業ツリーの差分レビューと land（commit / push / PR）

効果 5.0 コスト 4.5

いま ukai がレビューできるのは エージェントが ACP で報告した差分だけ（ukai_core::review）。ツール呼び出しの外で起きた変更、報告を落としたエージェント、Pod の中で複数ターンにわたった変更の合計は見えないし、見終わったあと commit も PR もできない。orca と hermes はどちらもここが本体（hermes の Review Desk はターン単位 / ファイル単位 + risk flag、Land は commit → PR を 1 操作）。

なぜ最優先
gateway でエージェントを Pod の中で動かす設計なので、作業ツリーがユーザーの手元にない。「成果を取り出す」経路が UI に無いと、クラウド実行そのものが使い物にならない。
入れる場所
ukai-core に git モジュール（差分の取得は純粋関数側に寄せ、既存の review::hunks / review_prompt をそのまま再利用）。ローカルプロジェクトは手元の git、gateway のワークスペースは relay に _ukai/workspace 系のメソッドを足して差分と commit / push を代行させる（git credential は既に workspace サイドカーとエージェントにしかない前提を崩さない）。
注意
PR 作成はエージェント自身が gh でできる（既に credential helper が向いている）。UI からやるときに ukai 側へ token を持ち込まないこと。
06

自動再接続と取りこぼしの補完

効果 4.6 コスト 3.0

SDK の HTTP クライアントは SSE が切れても自動ではつなぎ直さない。いまは「切断を UI に出して Resume を押させる」まで（design.md の Phase 5）。orca は SSH worktree の自動再接続を売り、herdr は切断に耐えることが存在理由。クラウド一級を謳う ukai が手動なのは弱い。

入れる場所
ukai-acp の接続タスクに指数バックオフの再接続、復帰は既存の SessionOptions::restore → RestoreOutcome 経路をそのまま使う。relay が履歴を持っているので gateway 経由なら取りこぼしは session/load の再生で埋まる。
見せ方
再接続中は Status に Reconnecting を足して、既存の状態ドット（黄 / 緑 / 橙 / 赤 / 灰）の語彙に載せる。
03

要対応エージェントへのジャンプ

効果 4.2 コスト 1.0

ukai は未読（ukai_core::Alert）とサイドバー・タブ・pane ヘッダのバッジを持っているが、「次に自分を待っているものへ行く」操作がない。hermes は ⌘I の 1 キー、herdr はサイドバーの blocked ロールアップ。pane が増えるほど効くのに、ほぼ無料で入る。

入れる場所
ukai-core に「未回答のパーミッション → 未読 → エラー切断」の順で次の pane を返す純粋関数（Transcript::awaiting_permission が既にある）。app.rs に mod+i、パレットにも項目を 1 つ。
04

実行中でも次のプロンプトを積める（キュー）

効果 3.9 コスト 1.3

いま Status::Busy の間は入力欄も送信ボタンも disabled（agent_pane.rs）。競合は 3 つとも打ち込んでおける。複数 pane を回す使い方では「思いついたときに書けない」が一番効く摩擦。

入れる場所
pane スコープの下書きを Vec<Prompt> のキューにして、TurnEnded で先頭を送る。キューは入力欄の上に（レビューコメントと同じ場所に）積んで、個別に取り消せるようにする。添付とレビューコメントもキューの要素に載せる。
01

セッションモードとモデルの選択・表示

効果 4.0 コスト 1.7

ACP はセッションモード（plan / edit など）とその切り替えを持っているのに、ukai は SessionEvent に項目がなく、モードを出すことも変えることもできない。hermes はタスクごとにエージェント・モデル・effort・アカウントを選んで preset 保存、orca はアカウント切り替えと使用量表示。ukai はプロトコルに既にある情報を捨てているだけなので、素直に埋めるのが一番安い。

入れる場所
ukai-acp の SessionEvent::Ready に利用可能なモード一覧、ModeChanged を追加。SessionHandle に set_mode。Transcript が現在のモードを持ち、pane ヘッダに出す。パレットから切り替えられると hermes の preset 相当が代替できる。
確認事項
モデル選択が ACP v1 の範囲か v2 待ちかは要確認。docs/design.md の open question に足す。
02

slash コマンドと @ ファイル補完

効果 3.6 コスト 2.0

ACP はエージェントが使えるコマンド一覧を通知で送ってくる。ukai はそれを無視しているので、/review のようなコマンドを CLI で覚えている人が ukai に来ると機能が消えたように見える。競合 3 つはターミナルなのでエージェント本来の UI がそのまま出る（彼らが得をしている構造的な点）。

入れる場所
ukai-acp で available commands を拾って Ready / 更新イベントに載せ、入力欄の / 補完に出す。@ のファイル補完は ukai_core::palette のあいまい検索をそのまま使える（添付の resource_link 経路に繋げる）。

P1 — 次に

07

タスク = ブランチ / worktree の第一級化

効果 4.4 コスト 4.0

3 製品共通の骨格。ukai の gateway は既にワークスペースを（利用者・namespace・リポジトリ・ref・コマンド・pane の鍵）のハッシュで分けているので、ref を UI から選べるようにするだけで 8 割が揃う。ローカルプロジェクトについては「pane を開くときに worktree を作る」を足す。

入れる場所
ukai-gateway/src/job.rs のワークスペース識別子に branch / ref を含める（既に ref は入っている）。UI 側は pane を開くダイアログで「新しいタスク名 → ブランチ」を入れる。Projects が「ルート + 不透明な id」なのは worktree を同じプロジェクトに束ねる前提で設計済み（design.md にその意図が書いてある）ので、モデル変更は小さい。
依存
提案 5（land）と組で初めて価値が出る。
08

ukai CLI / ローカル socket API

効果 3.9 コスト 2.9

herdr の socket API（pane.* / agent.* / events.subscribe）と orca の CLI は、エージェント自身がクライアントを操作するための面。ukai でこれがあれば「レポートを書いたエージェントが、それを隣の pane に開く」「エージェントが別エージェントの pane を立てて結果を待つ」ができる。HTML レポートが主要ユースケースである ukai とは特に相性がいい。

入れる場所
ukai-app が $UKAI_STATE_DIR/ukai.sock を listen し、open-report / open-agent / prompt / layout を受ける。ハンドラは ukai-core の Layout 操作に落ちるので、ロジックは headless にテストできる。
注意
このソケットは UI を外から操作できる口なので、ファイルパーミッション 0600 とプロジェクトルート外のパス拒否は最初から。gateway の Pod の中のエージェントには届かない（届かせない）。
12

チェックポイントとターンの巻き戻し

効果 3.6 コスト 4.2

hermes はターン単位で diff と restore、orca は snapshot。ukai は relay が既に refs/ukai/wip/<id> へ定期・ターン終了・停止時に snapshot を push している。材料はあるのに復元 UI がないのがもったいない。

入れる場所
relay の snapshot をターン id で名前付きにして、_ukai/checkpoints で列挙と復元を出す。UI は transcript のターン境界に「ここまで戻す」。ローカルプロジェクトでは 提案 5 の git モジュールで同じことをする。
10

会話ジャーナルの永続化と横断検索

効果 3.4 コスト 3.0

ukai は会話を保存せず、再起動後は session/load → session/resume → 新規の順で復帰する。loadSession を広告しないエージェントでは履歴が消える。orca は会話ジャーナル DB を持ち、横断検索も売りにしている。design.md が「SQLite を入れる条件」として挙げている状況そのもの。

入れる場所
state.json には混ぜず、追記専用のジャーナルを別ファイルに（design.md の方針どおり）。Transcript の fold が純粋関数なので、ジャーナルの再生でそのまま復元できる。
09

terminal/* の client capability

効果 3.3 コスト 3.4

ukai は terminal/* を広告していない（初期の方針）。しかし競合 3 つはどれもターミナルが本体で、ユーザーは「エージェントが走らせたコマンドの出力を見たい」。ターミナル pane を作る（= 多重化器になる）のではなく、ACP の terminal/* に応えて、出力を transcript のツール呼び出し行として見せるのが ukai らしい落とし方。

入れる場所
ukai-acp に fs.rs と同じ構えで terminal.rs（プロジェクトルート内で実行、出力をリングバッファ）。Transcript に出力付きのエントリ。gateway 経由ではエージェント側に terminal を広告しない現状の方針と矛盾しないか要整理。
保留の理由
任意コマンド実行を ukai が担うことになるので、パーミッション規則（Phase 5）より後。
11

1 プロンプトを複数 pane に fan-out して比較

効果 3.0 コスト 1.9

orca の「1 つのプロンプトを 5 つのエージェントに投げ、結果を比べて勝者を merge」。ukai はタブに別エージェント・別プロジェクトを並べられるので、「このタブの全 agent pane に同じプロンプトを送る」だけで成立する。鵜飼という名前にも合う。

入れる場所
パレットのコマンド 1 つ（「タブ内の全エージェントに送る」）+ 入力欄のトグル。送信先は Layout からそのタブの agent pane を列挙するだけ。
依存
比較して選ぶところは提案 5 の差分レビューが前提。
13

pane のリサイズとフォーカス移動キー

効果 2.8 コスト 1.2

競合は全部持っている。ukai は Layout の split が既に子ごとの比率を持っているので、境界のドラッグを足すだけ（design.md にも「今後」として明記）。あわせて mod+矢印 の pane 間フォーカス移動も。現状のショートカットは mod+k/t/d/w の 4 つだけで、キーボードで pane を渡り歩けない。

入れる場所
ukai-core/src/layout.rs に比率の更新（不変条件はプロパティテストで既に守られている）、app.rs のショートカットに方向キー。

P2 — 後で / 条件付き

16

ブラウザ pane と要素ピック → プロンプト（orca Design Mode 相当）

効果 2.9 コスト 3.7

orca は worktree ごとに実 Chromium を持ち、クリックした要素の HTML / CSS / スクショをプロンプトに流し込む。ukai は report_pane.rs に IPC を持たない子 WebView という土台を既に持っているので、URL を読めるようにすれば近いことができる。フロントエンドを書かせる用途では強い。

注意
要素を取るには子 WebView に script を注入して結果を受け取る必要があり、「IPC ハンドラを持たせない」という現在の安全保証を崩す。別オリジン（任意の web）を読む pane を足すなら、レポート pane とは別の種別として設計しないと危ない。
17

リモート UI（ブラウザ / モバイルから覗く）

効果 2.6 コスト 5.0

orca のモバイルコンパニオン（完了通知 + 追い指示）、herdr の SSH attach。ukai はセッションがサーバー側で生きているので、原理的には一番筋がいい（gateway に別のクライアントがつなげばよい）。Dioxus の web ターゲットもある。ただし認証・レポート配信・子 WebView 前提の描画をすべて作り直すことになるので、コアが固まってから。

15

GitHub の issue / PR から pane を開く

効果 2.5 コスト 3.6

orca は GitHub / Linear をアプリ内に持ち、issue から worktree を開く。gateway が ref を指定して clone する作りなので「この PR のブランチでエージェントを開く」は自然に繋がる。ただしアプリ内ブラウズまで作ると IDE 化するので、「issue / PR を選んでタスクを開く」だけに絞る。gh を呼ぶ形にすれば token を ukai が持たずに済む。

使用量 / レート制限の可視化

効果 2.4 コスト 2.4

orca はアカウント切り替えと Claude / Codex の使用量・リセット時刻を出し、hermes は複数アカウントを扱う。ukai の認証はヘッダの ${env:...} 参照だけなので、まず ACP 側に usage を運ぶ場所があるかの確認から。無ければ見送り。

意図的に取り込まないもの

  • コードエディタ / LSP。 orca は VS Code のエディタを積んでいるが、ukai の non-goal のまま。差分レビュー（提案 5）で読めれば足りる。
  • ターミナル多重化器になること。 herdr の領域。ukai が PTY を並べ始めると ACP ネイティブである意味が薄れる。terminal/* への応答（提案 9）までに留める。
  • プラグインマーケットプレイス。 pre-alpha で拡張点を固定するのは早い。CLI / socket API（提案 8）が同じ需要の 8 割を吸う。
  • エージェントのプリセットを 40 個同梱すること。 ukai の [agents.<id>] は宣言的で、ユーザー設定に層として重ねられる。同梱するなら ukai.toml の例を増やすだけでよい。
